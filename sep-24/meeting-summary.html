The workflow on the whiteboard

The PRD comes first because it says what the business needs. TASKS.md turns the PRD into a board you move as you work, so anyone can see what's done and what's next. The spec says what you're building and why, and the plan says how, in steps small enough to check. You commit the spec and plan before any code, since a wrong decision is cheapest to fix before anything is built.

The build has two ways to run. Inline execution is what the tutorial had you use. Claude does every task in your own session, you watch each test and file go by, and it stops where you tell it to. Subagent-driven execution hands each task to a fresh helper agent that starts with a clean slate. A reviewer agent then checks the work against the spec before the next task starts. It's faster and keeps early mistakes from carrying forward, but the work happens where you can't see it. You'll probably use it on the capstone, and having watched inline first means you'll know what the subagents are doing.

Each milestone gets its tests, its code, and a commit that starts with its TASK id. Then the work is reviewed, merged into main, pushed, and deployed to the live app.

Questions to ask your coding agent about your own repo

For each step on the board, I asked a question you can put to Claude Code or Codex about your own tutorial repo. If you can follow the answer and explain it in your own words, you understand that step.

Key takeaways

  • The order matters: PRD, board, spec, plan, and only then code.
  • Read the spec like you'll have to defend it, because on the capstone you will.
  • Inline execution is for learning, and subagent-driven execution is for real work once you know what it's doing.
  • The tutorial handed you a PRD. On the capstone, you'll have to discover and confirm what belongs in one, which is where the Oct 1 session picked up.
